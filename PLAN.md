## 0. Цель и критерии готовности

**Цель:** заменить PHP-CMS на статический сайт Hugo, который выглядит как текущий сайт, плюс несколько динамических модулей на Go.

**Сайт готов (релиз R1), когда:**
- каждый URL из таблицы инвентаризации отдаёт 200 или 301 (без 404);
- визуальное расхождение с оригиналом ≤ 2 % на эталонных страницах (новый формат);
- legacy-страницы отображаются в новом дизайне;
- все файлы `/file/` на месте, SHA-256 совпадает с origin;
- 0 битых внутренних ссылок;
- служебные файлы в корне работают (RSS, SendPulse, Google verification, robots).

## 2. Архитектура

```
origin $ORIGIN_HOST
  ├─ HTML-страницы CMS ── краулер ──► raw/pages + inventory.csv
  └─ file/ img/ css/ … ── rsync ────► /srv/firebirdsql/assets (VM) и локально
                                         │
raw/pages ── converter ──► site/content/**.md ── hugo + pagefind ──► public/

                ┌────────── nginx на дроплете DigitalOcean (без Cloudflare) ───┐
  браузер ─────►│ /file/, /img/, /template/ … → /srv/firebirdsql/assets (alias) │
                │ /                            → public/ (текущий релиз)         │
                │ /api/<module>/…              → Go-сервисы (JSON, POST форм)    │
                │ /en/<dyn-path>               → Go-сервисы (HTML целиком)       │
                └────────────────────────────────────────────────────────────────┘
```

### 2.1. Правила URL
- URL не меняются. Сейчас есть оба вида: `/en/downloads/` (со слэшем) и `/en/news` (без слэша).
- Hugo создаёт `path/index.html`. nginx: `try_files $uri $uri/index.html $uri.html =404;` — оба вида работают **без редиректа**.
- Для каждой страницы в таблице хранится каноническая форма URL → `<link rel="canonical">` на `https://firebirdsql.org/...`.
- Пагинация и query string (`?page=2` и т. п.): краулер нормализует, конвертер сопоставляет со схемой Hugo; старые адреса → 301 в nginx (`map`).
- Абсолютные ссылки на `firebirdsql.org`, `www.`, `cms.`, `cms-*.` в контенте → относительные.

### 2.2. Динамические модули (Go + JS)

| Способ | Как работает | Пример |
|---|---|---|
| **A. Форма** | Статическая страница + форма; `POST /api/<module>` → JSON | Отправка вопроса |
| **B. Остров** | Статическая страница; JS запрашивает `GET /api/<module>/…` | Калькулятор конфигурации |
| **C. Динамическая страница** | nginx отдаёт путь целиком Go-сервису; сервис рендерит HTML в shell-шаблон | Анализ трейса и статистики, демо экзамена |

Список модулей (решение 10):

| Модуль | Способ | Путь (предварительно) | Релиз |
|---|---|---|---|
| Отправка вопроса | A | форма на `/en/support/` и др., `POST /api/ask` | R2 |
| Калькулятор конфигурации | B | `/en/config-calculator`, `GET/POST /api/calc` | R3 |
| Инструменты анализа трейса и статистики Firebird | C | `/en/tools/trace/…`, `/en/tools/stat/…` | R3 |
| Демо сертификационного экзамена | C | `/en/certification/exam-demo/…` | R3 |

- **Shell-шаблон:** Hugo собирает `public/_shell/base.html` (тот же `<head>`, шапка, меню, футер) с маркерами `{{TITLE}}`, `{{META}}`, `{{CONTENT}}`. Сервисы перечитывают его после каждого деплоя. Дизайн меняется в одном месте.
- **Реестр** `site/data/dynamic.yaml` (модуль, способ, пути, upstream) → из него генерируются `location` nginx и fallback-страницы.
- **Fallback:** сервис недоступен → `error_page 502 503 504` → статическая страница в дизайне сайта.
- **Безопасность:** проверка `Origin`, `limit_req` в nginx, honeypot / hCaptcha (без Turnstile), валидация на сервере, лимит размера вложений, секреты только в env.
- **Данные:** где нужна БД — Firebird.
- **Сервисы:** один Go-бинарник с модулями, пока модулей ≤ 4; отдельные сервисы — если больше.

## 4. Этапы

Для каждого этапа указан **результат** — условие, при котором этап закрыт.

### Этап 0. Репозиторий и инфраструктура (1–2 дня)
1. `git init`, репозиторий на GitHub, `.gitignore` (`raw/`, `public/`, assets).
2. **Дроплет DigitalOcean** `s-1vcpu-1gb`, регион `ams3`, Ubuntu 24.04 LTS, имя `fb-web-1`. Создание скриптом `deploy/do/create.sh` (`doctl compute droplet create … --user-data-file cloud-init.yaml --ssh-keys …`), чтобы дроплет можно было пересоздать. Токен читается из `$DO_TOKEN_FILE` (или `DIGITALOCEAN_TOKEN` в секретах CI), в репозиторий не попадает.
   - Новый SSH-ключ для дроплета → загрузить в DO (`doctl compute ssh-key import`).
   - **DO Cloud Firewall:** вход 22 (только с ваших IP), 80, 443; выход — всё.
   - Reserved IP (бесплатно, пока привязан) — DNS указывает на него; пересоздание дроплета без смены DNS.
   - cloud-init: swap 2 ГБ, пользователь `deploy`, SSH только по ключу, fail2ban, unattended-upgrades.
3. На дроплете: nginx, certbot, Docker (для R2+), каталог `/srv/firebirdsql/{releases,assets}`. Hugo и Pagefind на дроплет **не ставим** — сборка в CI, на дроплет приходит готовый `public/`.
4. **Тестовый сайт `newtest.firebirdsql.org`** на дроплете (решение 12): тот же nginx-конфиг, `X-Robots-Tag: noindex` и `robots.txt` с `Disallow: /` (только для newtest), по желанию basic auth.
   - Порядок: создать дроплет → Reserved IP → вы настраиваете DNS `newtest` (A-запись, **без proxy Cloudflare**) → certbot выпускает сертификат → первый деплой.
   - До DNS проверка по IP: `curl --resolve newtest.firebirdsql.org:80:<IP> http://newtest.firebirdsql.org/`.
   - Локально для разработки: `hugo server` и `docker compose up` (nginx + `public/` + assets + Go-сервисы).
5. На origin: пользователь `mirror` с доступом **только для чтения** к docroot (`rrsync -ro`), отдельный ключ. Ключ root в CI не используем.

**Результат:** `ssh mirror@origin` даёт только rsync на чтение; `https://newtest.firebirdsql.org/` открывается с валидным сертификатом и `noindex`.

### Этап 1. Инвентаризация (1–2 дня)
1. **rsync статики** (на дроплете, прямо с origin; локально — в WSL, в Git Bash на Windows rsync нет):
   `rsync -az --delete --exclude='.svn/' --exclude='*.svn-base' -e 'ssh -p $ORIGIN_PORT -i <key>' mirror@$ORIGIN_HOST:/var/www/cms.firebirdsql.org/docroot/{file,img,css,js,template,plugins,doclibs,book,security,doctools,lst_files} /srv/firebirdsql/assets/`
   плюс служебные файлы корня и `static/rss/`.
   - Защита от ошибки на origin: сначала `--dry-run`; если удаляется > 2 % файлов — остановка и уведомление.
   - Манифест `file-manifest.csv` (путь, размер, SHA-256) на обеих сторонах, сравнение.
2. **Краулер HTML** (Go): старт с `/`, `/map`, RSS, а также `/pt/news` (только чтобы собрать pt-URL для редиректов, контент pt не конвертируем); обход всех внутренних ссылок (не только `/en/`). 2–4 запроса/с, User-Agent `fb-static-mirror`. Дополнительно — URL из Wayback Machine (`web.archive.org/cdx`) для поиска страниц без входящих ссылок.
   - Краулер не скачивает то, что уже есть в rsync, но проверяет, что каждая ссылка на `/file/`, `/img/` и т. д. есть в манифесте.
3. **Определение формата** (`scraper/formats.yaml`): `new` (`/template/css/style.css` + `header-area`), `legacy` (`/css/site.css` или `content_menu`), `unknown` → ручной разбор. Проверить кодировку legacy-страниц.
4. Результат — **`inventory.csv`**:

   | url | status | kind | lang | format | canonical | title | date | sha256 | links_in | links_out | target |
   |---|---|---|---|---|---|---|---|---|---|---|---|
   | `/en/firebird-5-0` | 200 | page | en | new | … | … | … | … | … | … | converted |
   | `/map` | 200 | page | en | legacy | … | … | … | … | … | … | redirect → … |
   | `/file/…/firebird-5-quickstartguide.pdf` | 200 | file | — | as-is | … | … | … | … | … | … | as-is |

   `kind`: page / file / asset / root-file; `format`: new / legacy / unknown / as-is; `target`: converted / redirect / manual / as-is.

**Результат:** отчёт — число страниц по формату и языку, битые ссылки, внешние ссылки, страницы без входящих ссылок.

### Этап 2. Анализ шаблонов и источник данных (1–2 дня)
1. Сгруппировать страницы по структуре DOM: новость, список, статическая страница, продукт, таблица загрузок, legacy.
2. Селекторы контента для каждого типа → `scraper/selectors.yaml`.
3. **Проверка БД CMS (spike, строго ≤ 0.5 дня):** место БД неизвестно (поиск `*.fdb` ничего не дал). Искать строку подключения в коде CMS (`docroot/cms/`, `index.php` и подключаемые файлы), алиасы в `/etc/firebird/3.0/databases.conf`, открытые файлы процесса `firebird` (`ls -l /proc/<pid>/fd`). Если за 0.5 дня не нашли или нет доступа — **только HTML**. Если нашли — брать из БД метаданные (даты, slug, порядок меню); тело страниц всё равно из HTML.

**Результат:** селекторы покрывают 100 % страниц со статусом `new`/`legacy`; решение «HTML only» или «HTML + метаданные из БД».

### Этап 3. Конвертер (2–3 дня)
1. Front matter: `title`, `date`, `slug`, `url`, `lang`, `image`, `summary`, `description`, `type`, `weight`, `menu`, `aliases`.
2. Тело: HTML → Markdown, сложные блоки (таблицы загрузок, вкладки) — raw HTML (`markup.goldmark.renderer.unsafe = true`).
3. Сохранить `<title>`, `meta description`, OpenGraph из оригинала.
4. Меню и футер → `site/data/menu.yaml`, `footer.yaml`.
5. Идемпотентность: тот же вход → тот же выход. В переходный период ручные правки в `content/` запрещены (их затрёт синхронизация); правки — в CMS или в конвертере.

**Результат:** `hugo` собирает сайт без ошибок и предупреждений; число страниц = числу `converted` в `inventory.csv`.

### Этап 3а. Legacy → новый формат (2–4 дня)
1. Селекторы legacy: заголовок, `content_menu_breadcrumbs`, `content_menu_nav`, тело.
2. Берём только контент; шапка, меню, CSS — от нового шаблона.
3. Чистка: inline-стили, `bootstrap-grid` → классы Bootstrap 4, lightbox → magnific-popup, FA5 (`fas fa-…`) → FA4 (`fa fa-…`) по таблице.
4. Есть аналог в новом формате → 301; нет → тот же URL в новом дизайне.
5. `target = manual` → список для ручной проверки.
6. `/css/site.css` и `/plugins/` нужны только файлам `/file/` (если ссылаются) — страницы Hugo их не подключают.

**Результат:** ни одна страница Hugo не подключает `/css/site.css`; список `manual` проверен человеком.

### Этап 4. Тема Hugo `fireweb` (3–4 дня)
1. `baseof.html` — `<head>`, шапка, меню, футер из оригинала; оригинальные CSS/JS из assets.
2. Шаблоны: главная (слайдер, блоки), news list + пагинация как в оригинале, news single, страница по умолчанию, downloads, shop list.
3. Shortcodes: кнопка загрузки, вкладки (`tab-min.js`), галерея, YouTube.
4. Один язык — en. Мультиязычность Hugo не включаем. `/pt/...` → 301 по таблице (`target = redirect`), `/rss/pt/news.xml` → 301 на `/rss/en/news.xml`.
5. RSS по старому адресу `/rss/en/news.xml` (свой output format), `sitemap.xml`, `robots.txt` (от www + ссылка на sitemap), `404.html` в дизайне сайта.
6. Поиск: **Pagefind** по `public/` **и** по HTML-документам `/file/` (отдельный индекс, 6404 файла) — иначе документация пропадёт из поиска. Google-поиск — запасной вариант.
7. Shell-шаблон `_shell/base.html` (нужен для R2, делаем сразу — он почти бесплатный).

**Результат:** все типы страниц отрисованы; Lighthouse не хуже оригинала.

### Этап 5. Проверки (2 дня)
1. Playwright + `pixelmatch`: ~30 эталонных страниц (new), ширины 375 / 768 / 1440, порог ≤ 2 %.
2. Legacy: сравнение с эталонной страницей нового формата (шапка, меню, футер).
3. `lychee` или `htmltest` по `public/` + assets: 0 битых внутренних ссылок.
4. Каждый URL из `inventory.csv` на `newtest.firebirdsql.org` → 200 или 301.
5. Манифест SHA-256 assets на VM = манифест origin.
6. SEO: canonical, `<title>`, description, 404 возвращает код 404, `robots.txt` разрешает индексацию (только на production).

**Результат:** все проверки зелёные в CI; отчёт с diff-картинками.

### Этап 6. Развёртывание и переключение (1–2 дня)
1. CI (GitHub Actions): `rsync assets → crawl → convert → hugo --minify → pagefind → проверки этапа 5 → deploy`.
2. Деплой атомарный: `releases/<timestamp>` + переключение symlink `current`; хранить 5 последних релизов; откат = переключить symlink.
3. TLS: Let's Encrypt (certbot), автопродление, мониторинг срока.
4. Переключение DNS:
   - за 2 дня снизить TTL до 300 с;
   - перевести `firebirdsql.org` и `www` с Cloudflare (proxy) на Reserved IP дроплета;
   - **откат:** вернуть DNS на Cloudflare / старый сервер (старый сервер не выключать до R4).
5. Мониторинг: uptime (внешний сервис), 5xx в логах nginx, свободное место на диске.
6. Резервные копии: DO Backups (еженедельно, +$1.20/мес) + копия `/srv/firebirdsql/assets` в **DO Spaces** (`rclone sync`, $5/мес за 250 ГБ). После R4 это **единственная** копия файлов. Альтернатива Spaces — бесплатно оставить копию на текущем сервере origin.
7. Нагрузка на 1 ГБ RAM: nginx отдаёт статику (`sendfile`, `gzip_static` — сжатие заранее в CI, `open_file_cache`, кэш браузера для `/file/`, `/img/`, `/template/`). Monitoring agent DO: алерты CPU > 80 %, RAM > 85 %, диск > 80 %.

**Результат:** production на дроплете, откат проверен на `newtest` до переключения DNS основного домена.

### Этап 7. Переходный период (CMS — источник), 1 месяц
1. CI по расписанию **раз в сутки** (ночью): весь конвейер этапа 6. Через 1 месяц после R1 — этап 10.
2. Изменения `content/` после синхронизации — коммит в git (история правок).
3. Проверки не прошли → деплоя нет, уведомление.
4. Удалённые в CMS страницы → удаляются из `content/` + 301 или 410 по решению.

### Этап 8. R2 — каркас динамических модулей и формы (4–6 дней)
1. `dynamic.yaml` → генератор `location` nginx, `limit_req`, `error_page`.
2. Go-библиотека `dyn/common`: shell-рендер, JSON, валидация, rate limit, SMTP, health-check `/api/<module>/health`, логи JSON.
3. `docker-compose.yml`: локально nginx + статика + сервисы; `hugo server` проксирует `/api`.
4. **Модуль «Отправка вопроса» (A):**
   - Поля: имя, e-mail, тема, версия Firebird, ОС, текст вопроса; согласие на обработку данных.
   - `POST /api/ask` → письмо на адрес поддержки (SMTP) + копия-подтверждение отправителю.
   - Защита: honeypot, hCaptcha, `limit_req` (например 5 в минуту с IP), проверка `Origin`, максимум 10 000 символов.
   - Без JS форма тоже работает (обычный POST → страница «Спасибо» в shell).

**Результат:** форма работает локально в `docker compose`; при остановке сервиса показывается fallback с e-mail.

### Этап 9. R3 — модули на Go (оценка после ТЗ на каждый модуль)
- **Калькулятор конфигурации (B)** — `/en/config-calculator`, `/api/calc`. Ввод: версия FB 3/4/5, архитектура (SuperServer / Classic / SuperClassic), RAM, CPU, число соединений, размер БД, page size. Вывод: `firebird.conf` / `databases.conf` (`DefaultDbCachePages`, `TempCacheLimit`, `LockHashSlots`, `FileSystemCacheThreshold` и др.), «скопировать», «скачать .conf». Логика на сервере.
- **Анализ трейса и статистики Firebird (C)** — пользователь загружает trace-лог или вывод `gstat` / мониторинга → Go разбирает → HTML-отчёт в shell (топ запросов по времени, чтениям, частоте; таблицы и индексы).
  - Загрузка больших файлов: потоковый разбор, лимит размера (например 200 МБ, nginx `client_max_body_size`), сжатые `.gz`/`.zip`.
  - **Конфиденциальность:** логи содержат SQL и данные клиентов. Файлы не хранить после разбора (или хранить ≤ 24 ч с удалением по таймеру), ссылка на отчёт — случайный ID, предупреждение на странице.
  - Ресурсы: очередь задач, лимит CPU/RAM контейнера, таймаут разбора, не больше N одновременных задач.
- **Демо сертификационного экзамена (C)** — без регистрации: случайный набор вопросов из банка, таймер, ответы, страница результата с разбором.
  - Банк вопросов — YAML в git или Firebird; демо-вопросы отдельно от настоящего экзамена.
  - Состояние сессии — подписанная cookie или запись в БД с TTL; защита от подбора — rate limit.
- **Shop:** до R3 — как сейчас (статика + ссылки на оплату).

### Этап 10. R4 — переход на Markdown (1–2 дня)
1. Последняя синхронизация, CMS только для чтения.
2. Убрать `crawl`/`convert` из CI; `site/content/` — единственный источник. Assets — только на дроплете + DO Spaces.
3. Инструкция для авторов: новость, картинки, превью, PR → проверка → деплой.
4. `scraper/`, `converter/` остаются в репозитории для архива. Старый сервер выключить через 1 месяц после R4.

## 7. Риски

| Риск | Мера |
|---|---|
| Без Cloudflare нет защиты от DDoS и CDN-кэша | Статика выдерживает много запросов; `limit_req`, DO Cloud Firewall; при атаке — быстро включить proxy Cloudflare обратно (DNS) |
| Скопирован `robots.txt` от `cms.` (`Disallow: /`) | Брать файл от www; проверка в этапе 5 |
| rsync `--delete` удалит файлы, если на origin что-то сломалось | `--dry-run` + порог 2 % + манифест |
| Root-ключ в CI | Пользователь `mirror`, `rrsync -ro`, отдельный ключ |
| Много legacy-страниц | Оценка после этапа 1; `manual` — по приоритету (трафик, входящие ссылки) |
| После R4 файлы `/file/` есть только на дроплете | DO Spaces + DO Backups до выключения старого сервера |
| 1 ГБ RAM мало для модулей R3 (анализатор, Firebird в Docker) | Статика R1 и форма R2 помещаются; анализатор — 1 задача одновременно, потоковый разбор; при нехватке — resize дроплета до 2 ГБ (несколько минут простоя) |
| Анализатор трейса: в логах SQL и данные клиентов; большие файлы нагружают дроплет | Не хранить файлы, отчёт по случайному ID, лимиты размера/CPU/времени, очередь |
| Токен DO даёт полный доступ к аккаунту | Хранить только в `E:\secure\` и в секретах CI; для CI — отдельный токен с минимальными правами (scoped token) |
| Форма вопроса — цель для спама | honeypot + hCaptcha + `limit_req` |
| jQuery 1.12.4 с уязвимостями | Статический сайт без пользовательского ввода — риск низкий; обновить после R1 |
